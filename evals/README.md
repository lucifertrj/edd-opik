# Evaluation Dataset

The durable dataset lives in Opik. `rag-loop seed` reads `seed.jsonl` and pushes it into Opik via
the SDK (`client.get_or_create_dataset(...).insert(...)`) — it doesn't stay a local file, the file
is just the source of truth for what gets pushed. Each `rag-loop seed` run creates a new dataset
version rather than mutating the previous one in place.

Each line is a golden — a real question grounded in `data/aircraft_systems.pdf` plus its expected
answer taken directly from the document text:

```json
{"input": "question", "expected_output": "answer taken directly from the source PDF", "metadata": {"source": "aircraft_systems.pdf", "page": 11}}
```

`expected_output` must be lifted from the actual document, not invented. `metadata.page` is the
1-indexed PDF page the answer comes from, matching the page numbers the app cites in its own
answers, or `null` for a clean negative — a question with no answer anywhere in the source.
`rag-loop seed` validates the file (`input`, `expected_output`, `metadata` required) and creates a
new Opik dataset version — fix the file rather than working around the validator.

Each golden also carries `label` (`1` if `expected_output` is actually grounded in the document,
`0` if it isn't) and `critique` (why), from an audit of the goldens against the source PDF. This is
a property of the golden itself, fixed at labeling time — it is not a prediction about what any
live run's output will look like. `label == 0` items are the one case where it doubles as a live
check: since the question is unanswerable by construction, the only correct app behavior is a
refusal, and `_clean_negative_recall` in `src/rag_loop/evals.py` checks the Hallucination metric
stays low across that held-out set.

`rag-loop evaluate` / `rag-loop experiment-loop` run each golden's `input` through the live app
(real Gemini call, real Qdrant retrieval) and score the actual answer against `expected_output`
and the retrieved context — the expected answer is a reference for scoring, never substituted in
as the app's forced output.

## Growing the dataset from real traces

Once the app has been run for real (`rag-loop ask`, or scenarios through the app), real production
traces are the better source for new items than more hand-picked PDF passages — they show what
users actually ask and where the app actually struggles. `create_dataset_from_traces` in
`src/rag_loop/evals.py` pushes trace-derived items into the same Opik dataset via the SDK; wire it
up to pull from Opik trace search once there's a real corpus of traces to draw from.

## `results/` and `experiments.json`'s `result` field

`rag-loop run <name>` writes a local snapshot of that run's scores to `evals/results/<name>.json`
(aggregates plus every per-case input/expected/actual/score) — a cache of what Opik already
recorded, kept here so a keep/reject decision can diff two runs without re-querying the Opik API.
It also writes the decision back onto that entry in `experiments.json` as a `result` object
(`decision`, `reason`, `comparisons`). Both are regenerated by `rag-loop run`, so if `evals/results/`
is deleted, re-run the experiment rather than trying to reconstruct it by hand.
